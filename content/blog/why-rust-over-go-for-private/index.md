仕事ではGoやTypeScriptを書いている。プライベートではRustを書いている。

なぜわざわざRustなのか。聞かれるとうまく答えられないのだが、自分なりに整理してみたい。

## 仕事とプライベートで求めるもの

Goはシンプルで、認知負荷が低い。TypeScriptもJavaScriptの延長として書き始めやすい。学習曲線はRustと比べればなだらかで、チームに新しいメンバーが入っても立ち上がりが早い。仕事の言語としてこれは大きな強みだと思う。

ただ、プライベートで書くコードに求めているものは、それとは少し違う。

仕事で求められるのは**生産性**だ。限られた時間でチームとして成果を出すこと。GoやTypeScriptはそこに応えてくれる。一方、プライベートで自分が求めているのは**成長実感**だと思う。書いていて手応えがあること。考えさせられること。あえて認知負荷が高い言語に向き合うことで得られるものがある。

GoやTypeScriptが悪い言語だという話ではまったくない。文脈が違えば、求めるものも違うというだけの話だ。

## Rustの面倒くささ

Rustは面倒くさい。所有権、借用、ライフタイム。コンパイラは容赦なくエラーを出してくる。

最初はかなり抵抗があった。GoやTypeScriptでは通るようなコードが、Rustではことごとくコンパイルに弾かれる。特にGoでは、メモリ管理や所有権を意識せずとも動く状態に持っていきやすいが、Rustではそうはいかない。

でも、しばらく書いていると変わってくる。コンパイラのエラーメッセージを読む力がついてきて、「こう書けば良いのか」と分かる瞬間がある。コンパイラが厳しいのは、考えることを促してくれているからだと気づく。

この面倒くささは、自分にとっては**良い負荷**だ。仕事では効率が優先されるから、こういう負荷を楽しむ余裕はあまりない。プライベートだからこそ、じっくり向き合える。そして、コンパイルが通ったときの安心感はGoやTypeScriptとは質が違う。「なんとなく動いている」ではなく「考えた上で動いている」という感覚がある。

## エラーという体験の違い

GoとRustのエラーハンドリングは、書いていると体験がだいぶ違う。

Goでは、関数が値とエラーの2つを返す。

```go
value, err := doSomething()
if err != nil {
    return err
}
```

この `if err != nil` を何度も書く。本来はエラーごとに対処を考えるための設計だが、正直、お作法として書いている部分がある。エラーの戻り値を `_` で捨てたり、戻り値をすべて無視して呼び出せばコンパイルは通るし、動いてしまう（[Go Playgroundで確認できる](https://go.dev/play/p/io24YnMyZmP)）。そこに少し不安が残る。

Rustでは、成功と失敗が `Result<T, E>` という1つの型に包まれている。

```rust
match do_something() {
    Ok(value) => { /* 成功時の処理 */ },
    Err(e) => { /* 失敗時の処理 */ },
}
```

`match` で受け取る場合、`Ok` と `Err` の両方を網羅しないとコンパイルが通らない。`?` 演算子で早期リターンすることもできるが、いずれにしてもResultの中身に触れるにはエラーの存在を意識する必要がある。もちろんRustでも `.unwrap()` でパニックさせたり、`let _ =` で無視することはできる。ただ、それは意識的な選択であり、Goのように暗黙的に見落とすリスクとは質が違う（[Rust Playgroundで確認できる](https://play.rust-lang.org/?gist=eb9d1d7b90562d892fb90349b713e0a8)）。Goでも `errcheck` のようなリンターを使えば検出できるが、Rustではコンパイラが標準で警告してくれる。デフォルトの安全性が異なるのだ。この安心感は、Goでは得にくかったものだ。

しかも、このResult型は中身を取り出さずに変換していくこともできる。

## 箱のまま操作する面白さ

Goではビルダーパターン等でメソッドチェーンを使うことはあるが、OptionやResultのような型にコンビネータを連ねて変換を組み立てるイディオムはない。値を変数に入れて、都度エラーをチェックするのが基本だ。

Rustでは、OptionにもResultにもIteratorにも `.map()` や `.and_then()` がある。

```rust
// get_config() → Option<Config>
// u.name() → Option<String>（名前が未設定の場合がある）
let name = get_config()
    .map(|c| c.user)
    .and_then(|u| u.name());
```

中身を取り出さずに、変換をつなげていける。この「箱のまま操作する」感覚が面白かった。

RubyやKotlin、Swiftあたりでは馴染みのある感覚かもしれない。でもRustでは、それが型で守られている。`.map()` の中で型が合わなければコンパイルエラーになる。気持ちよく書けて、かつ安全。

さらに、API設計に一貫性がある。Iteratorで `.map().filter().collect()` を覚えると、Optionでも `.map().unwrap_or()` と同じ感覚で書ける。Resultでも同じだ。1つのパターンを覚えると、他の型でも同じように使えると気づく。知識が横につながっていく感覚がある。

## おわりに

所有権、Result型、メソッドチェーン。この記事で書いてきたことは、それぞれバラバラの機能に見えるかもしれない。でも、根底にあるのは同じ設計思想だと思う。考えることを要求し、考えたぶんだけ安全と表現力で返してくれる。

Rustの良さをすべて理解するにはまだ時間がかかると思う。ただ、この「ちょっと難しい」というところに、自分は惹かれている。仕事では求められない種類の負荷を、プライベートであえて選ぶ。それが自分にとっての成長実感であり、Rustを書く理由なのだと思う。
